# 一键实时排程 + DeepSeek 思考链 + Windows exe 无窗口修复

## 一、概述

本次交付三件事（用户已确认取舍）：

| 编号 | 需求                                  | 已确认的实现取舍                                                                                              |
| -- | ----------------------------------- | ----------------------------------------------------------------------------------------------------- |
| A  | 客户端「一键实时排程」，服务端立即重跑 AI 总结           | 仅重跑**当前登录用户**的已验证绑定                                                                                   |
| B  | 排程过程中在客户端**实时显示 DeepSeek 思考链**，默认折叠 | **真思维链 + 二次落库**：先流式调 `deepseek-reasoner` 展示 `reasoning_content`，结束后再用现有 `deepseek-chat` 生成结构化 JSON 落库 |
| C  | 思考链留存                               | **保存最近一次到服务端**，客户端可再次展开（不需要完整历史列表）                                                                    |
| D  | 修复 Windows exe 双击图标无窗口              | 见第五章                                                                                                  |

技术路线：新增一个 **SSE 流式端点**（`POST /api/v1/schedules/me/replan`），客户端用 `fetch` + `ReadableStream` 消费；不用 EventSource（无法带 `Authorization` 头，虽然服务端也支持 `?token=`，但 fetch 方案更整洁）。不用现有 WS Hub（Hub 的 `readLoop` 会读消息、语义是服务端单向推送，不适合透传模型流）。

### 3.6 `server/internal/summarize/replan.go`（新增文件）

1. `RunOptions` 增加字段（改 `summarize.go` 里的结构体）：

   并在 `RunForBinding` 的 `since` 计算处生效（`if state.LastSummaryAt != nil && !opts.IgnoreLastSummary`）。
2. 把 `RunForBinding` 的「准备段」抽成同文件私有方法，供两条路径共用：


   `RunForBinding` 改为 `prepareRun` + 原有落库逻辑（**行为保持不变**，含 `len(msgs)==0` 的短路分支移到 prepare 的调用方，避免语义漂移）。
3. `replan.go` 内实现流式一键排程：

   ```go
   // ReplanEmitter receives incremental progress of a manual replan.
   type ReplanEmitter interface {
       Phase(phase, message string) error        // reasoning | summarizing | persisting
       Delta(kind, text string) error            // kind: reasoning | answer
   }
   type ReplanResult struct {
       Revision  int64  `json:"revision"`
       NewItems  int    `json:"new_items"`
       Messages  int    `json:"messages"`
       Skipped   bool   `json:"skipped"`   // 无新消息
       Reasoning string `json:"reasoning"`
       Model     string `json:"model"`
   }
   func (s *Service) RunReplan(ctx context.Context, b store.Binding, opts RunOptions, em ReplanEmitter) (*ReplanResult, error)
   ```

   执行顺序：

   1. `prepareRun`（`IgnoreLastSummary=true`）。
   2. `em.Phase("reasoning", "正在阅读群聊消息并推断日程…")` → `ChatStream(ctx, system, prompt, StreamOptions{Model: c.ReasoningModel(), MaxTokens: 2048}, ...)`，把 `Reasoning` 增量转成 `em.Delta("reasoning", d)`、`Content` 增量转成 `em.Delta("answer", d)`。

      * 流式整体超时：`context.WithTimeout(ctx, 300*time.Second)`。

      * 失败**不致命**：记录 warning，继续第 3 步（思考链缺失但仍能出日程）。
   3. `em.Phase("summarizing", "正在生成结构化日程…")` → 沿用 `s.client.ChatJSON(ctx, system, prompt)`（`deepseek-chat` + JSON 模式，90s 超时；与 `RunForBinding` 一致）。
   4. 解析（`parseAIItems`）→ `BumpRevision` → `schedule.MergeAI` → `UpsertItem` → `SetLastSummaryAt` → `SetUserDigest`。
   5. `SetSummaryRunReasoning(run.ID, reasoningText, reasoningModel)`；`FinishSummaryRun(...)`。
   6. 返回 `ReplanResult`。

   * 失败路径同样要 `FinishSummaryRun(..., RunFailed, ...)`，并把 reasoning 尽力保存（只要流式拿到了内容）。

   * `len(msgs)==0` 时：`em.Phase("reasoning","该时间窗内没有与你相关的消息")`，`FinishSummaryRun(..., RunOK, 0,0, rev, "")`，返回 `Skipped=true`。

### 4.2 `client/src/services/api.ts`：流式请求

新增（不改动既有函数）：

```ts
/** 流式请求：不设整体超时，用外部 signal 主动取消（读 body 期间不会被超时打断） */
async function streamFetch(path: string, init: RequestInit, signal?: AbortSignal): Promise<Response>

replanStream: async (
  onEvent: (ev: ReplanEvent) => void,
  signal?: AbortSignal,
  lookback?: string
): Promise<void> => { /* POST /schedules/me/replan?... */ }

getLatestReplan: () => request<LatestReplan>('/schedules/me/replan/latest')
```

`replanStream` 要点：

* 头：`{ Accept: 'text/event-stream', 'Content-Type': 'application/json', ...authHeader() }`；body 传 `{}`。

* `!res.ok` → `throw await parseError(res)`（409 会被客户端提示为「已有排程在进行中」）。

* `res.body` 为空（老 WebView）→ 抛 `ApiError({status:0, message:'当前环境不支持实时流'})`。

* 消费：`const reader = res.body.getReader(); const dec = new TextDecoder('utf-8'); let buf = ''`；循环 `read()`，`buf += dec.decode(value, {stream:true})`，按 `\n\n` 切块；每块把以 `data:` 开头的行拼起来 `JSON.parse` → `onEvent`。**必须** **`try/finally { reader.cancel() }`** 保证取消时释放连接。

```ts
/** 一键实时排程：流式接收思考链，结束后强制刷新日程与提醒 */
export async function runReplan(): Promise<void> {
  if (useReplanStore.getState().status === 'running') return
  const ctrl = new AbortController()
  current = ctrl
  useReplanStore.getState().beginRun()
  try {
    await api.replanStream((ev) => useReplanStore.getState().applyEvent(ev), ctrl.signal)
  } catch (err) {
    if (!ctrl.signal.aborted) useReplanStore.getState().fail(errorMessage(err))
  } finally {
    current = null
    // 无论成败都刷新：成功则有新日程，失败也要保持数据一致
    await refreshNow().catch(() => undefined)
    await reschedule({ force: true, includeAlerts: true }).catch(() => undefined)
  }
}

export function stopReplan(): void { current?.abort(); current = null }

/** 页面首次挂载时拉取「上次思考链」 */
export async function loadSavedReplan(): Promise<void> {
  if (useReplanStore.getState().loaded) return
  try {
    const rec = await api.getLatestReplan()
    useReplanStore.getState().loadSaved(rec)
  } catch { /* 忽略：登出/离线时不影响主流程 */ }
}
```

`applyEvent` 里 `done` → `finish(ev.revision, 累计 newItems)`。

## 五、Windows exe 无窗口修复

### 5.1 根因（已通过实机日志确证）

> 旧代码 `.run(...).expect("启动 Tauri 应用失败")` + release 下 `windows_subsystem = "windows"` 无控制台 → 任何启动期错误都表现为「双击无窗口、无任何提示」。

**真实根因（2026-10-20 实机验证，`%LOCALAPPDATA%\QQSchedule\app.log` 抓到）：**

```
fatal: failed to initialize plugin `notification`:
Error deserializing 'plugins.notification' within your Tauri configuration:
invalid type: map, expected unit
```

即 `tauri.conf.json` 里的 `"plugins": { "notification": {} }` 类型非法（该插件不需要配置项，传对象会被反序列化拒绝）→ 插件初始化失败 → 旧代码 panic → 静默退出。**修复：删除整个 `plugins` 块**（见 5.2）。

其余两条为顺带排查项：
1. ~~托盘 id 重复~~（`app.trayIcon.id="main"` 与 Rust `TrayIconBuilder::with_id("main")`）—— 仍按「去重」处理，避免潜在冲突，托盘功能由 Rust 侧独享。
2. `--minimized` 参数未被读取（仅影响开机自启场景，不是双击场景，但顺手修）。

### 5.2 `client/desktop/src-tauri/tauri.conf.json`

* **删除整个** **`app.trayIcon`** **块**（保留 Rust 侧托盘，它带「显示主窗口/开机自启/退出」菜单，功能更全）。`bundle.icon` 保留不动。**同时删除整个 `plugins` 块**（`"notification": {}` 是本次崩溃的真正原因——该插件无配置项，传空对象会导致反序列化失败）。

## 七、假设与决策

| 决策                       | 说明                                                                                           |
| ------------------------ | -------------------------------------------------------------------------------------------- |
| 思考链取两份调用                 | 用户选择「真思维链 + 二次落库」。reasoner 只负责展示，落库仍走 `deepseek-chat` JSON 模式，保证日程写入的可靠性。总耗时约为原来的 2 倍，属已知代价。 |
| 一键排程只跑当前用户               | 用 `ListVerifiedBindingsByUser` + `Service.RunReplan`；不调用全量的 `RunIncrementalNow`。             |
| 忽略 `last_summary_at`     | 手动排程用 query 的 `lookback`（默认 168h）重读，否则「刚跑过」会导致空跑。                                            |
| 思考链只留最近一次                | `summary_runs` 新增两列，`GetLatestReplanRecord` 取最新一条；不做历史列表。                                    |
| SSE 而非 WS                | 复用现有 `fetch` 栈与 JWT 头；WS Hub 语义是服务端广播，不适合透传模型流。                                              |
| 流式用独立 `http.Client`      | 共享 client 的 90s 整体超时会掐断长流；流式改用只限制首字节的 transport。                                             |
| 模型名可配置                   | 新增 `deepseek.reasoning_model`，默认 `deepseek-reasoner`，服务端不用改代码即可回退。                           |
| 面板默认折叠                   | 用户明确「一般为折叠」；运行中头部显示阶段与新增数，用户主动展开才看全文。                                                        |
| exe 修复以「去重 + 容错 + 可诊断」为主 | 根因是假设（托盘 id 撞车），因此同时加上日志落盘，若首次修复未生效可据日志继续定位。不引入 single-instance 等额外依赖。                       |
